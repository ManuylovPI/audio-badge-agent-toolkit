## 1. Кодек по умолчанию и параметры

Кодек — Opus, и он единственный: без `CONFIG_OMI_CODEC_OPUS` сборка падает с `#error`.

| Параметр | Значение | Где |
|---|---|---|
| Кодек | Opus (другие не собираются) | `config.h:21-25`, включён в `omi.conf:213` |
| Codec ID в характеристике `19B10002` | **21** (1 байт) | `config.h:40`, отдаётся в `transport.c:354-356` |
| Частота дискретизации | 16000 Гц, моно | `codec.c:97` (`opus_encoder_init(..., 16000, 1, ...)`) |
| Длина кадра | 320 сэмплов | `config.h:28` (`160 * 2`), кодируется в `codec.c:134-135` |
| Битрейт | 32000 бит/с | `config.h:31`, применяется в `codec.c:98` |
| VBR | включён, без ограничения (`VBR_CONSTRAINT(0)`) | `config.h:32`, `codec.c:99-100` |
| Режим Opus | `OPUS_APPLICATION_RESTRICTED_LOWDELAY`, CELT | `config.h:30`, `config.h:35` |
| Complexity | 3 | `config.h:33`, `codec.c:101` |
| Тип сигнала / разрядность | `OPUS_SIGNAL_VOICE`, 16 бит | `codec.c:102-103` |
| DTX / in-band FEC / packet loss | всё выключено (0) | `codec.c:104-106` |
| Максимум байт на закодированный кадр | 160 | `config.h:29`, буфер `codec.c:52` |

- **[вывод]** Длительность кадра: 320 / 16000 = **20 мс**, то есть 50 кадров/с. Косвенно подтверждается приложением: для codec id 21 (`opusFS320`) оно считает 50 кадров/с и 320 сэмплов на кадр — `app/lib/services/devices/connectors/omi_connection.dart:430-431`, `app/lib/backend/schema/bt_device/bt_device.dart:77`, `:86`.
- **[вывод]** Средний размер кадра при 32 кбит/с и 20 мс ≈ 80 байт. Это расчёт: VBR не ограничен, реальный размер плавает, жёсткий потолок — 160 байт (`config.h:29`). Измерений в репозитории не искал.
- Микрофон: PDM, 16000 Гц, 16 бит — `omi/firmware/omi/src/mic.c:30-31`, `:212-214`. В кодек PCM подаётся блоками по 1600 сэмплов (100 мс) — `config.h:6`, `omi/firmware/omi/src/main.c:87`.

### Расхождения с документацией

- Док: значение codec type `20` = Opus 16 кГц, кода `21` в таблице нет (`Protocol.mdx:97-103`). Прошивка отдаёт **21**.
- Док: «Each audio packet contains 160 samples» (`Protocol.mdx:125`, `:141`). В прошивке кадр — **320** сэмплов.
- Док: «Starting with firmware v1.0.3, the default codec is Opus» (`Protocol.mdx:106`) — в части «Opus» совпадает с кодом; про номера версий в коде подтверждения не искал.

## 2. Заголовок аудиопакета

Каждое BLE-уведомление в характеристике `19B10001` начинается с 3 байт (`NET_BUFFER_HEADER_SIZE 3` — `transport.c:973`):

| Байты | Поле | Как формируется | Где |
|---|---|---|---|
| 0–1 | packet number, uint16 little-endian | `id = packet_next_index++`, младший байт первым | `transport.c:1082-1084` |
| 2 | index, uint8 | локальная переменная `index`, стартует с 0 на каждый кадр | `transport.c:1070`, `:1085` |
| 3… | полезная нагрузка — байты Opus-кадра | `memcpy` из буфера кадра | `transport.c:1086` |

Как растут счётчики (всё в `push_to_gatt`, `transport.c:1066-1131`):

- **packet number растёт на 1 на каждое уведомление**, а не на каждый аудиокадр. Инкремент стоит внутри цикла по фрагментам (`transport.c:1074`, `:1082`). Если кадр разбит на два уведомления, они получают номера `n` и `n+1`.
- **index — номер фрагмента внутри текущего кадра**: 0 у первого уведомления кадра, +1 на каждый следующий фрагмент (`transport.c:1089`), обнуляется при входе в функцию для следующего кадра (`transport.c:1070`).
- Счётчик `packet_next_index` — `static uint16_t` (`transport.c:1060`). **[вывод]** переполняется 65535 → 0 по типу; явного кода обёртки нет.
- Счётчик **не сбрасывается** при разрыве и переподключении: единственные обращения к нему во всём `omi/firmware/omi/src` — объявление (`transport.c:1060`) и инкремент (`transport.c:1082`). Обнуляется только при перезагрузке.
- Номер расходуется до попытки отправки. Если `bt_gatt_notify_cb` не удался 3 раза подряд, уведомление не уходит, а номер уже потрачен — у приёмника будет пропуск в нумерации (`transport.c:1082`, `:1092-1127`).
- При такой неудаче функция сразу возвращает `false`, оставшиеся фрагменты кадра не отправляются (`transport.c:1121-1127`).

### Противоречие в документации — что подтверждает код

- Описание полей: «Packet Number — Overall packet counter», «Index — Position of this value within the current packet» (`Protocol.mdx:137-138`). Отсюда естественно читать, что у фрагментов одного пакета номер одинаковый.
- Пример: «Notification 1: packet n, index 0; Notification 2: packet n+1, index 1» (`Protocol.mdx:146-147`) — номер растёт и внутри одного пакета.
- **Код соответствует примеру.** Точная формулировка: packet number — сквозной счётчик уведомлений; index — номер фрагмента в кадре. Начало нового кадра — это `index == 0`, а не смена packet number.

Переменная `current_package_index` (`transport.c:56`) объявлена, но в `omi/firmware/omi/src` больше нигде не используется.

## 3. MTU и фрагментация

### MTU

- Текущее значение хранится в `current_mtu` (`transport.c:55`) и берётся из `bt_gatt_get_mtu()`: при подключении (`transport.c:609-610`), в колбэке обмена MTU (`transport.c:502-506`), при повторной проверке (`transport.c:869-870`). При разрыве обнуляется (`transport.c:697`).
- Прошивка сама инициирует обмен MTU после подключения: `update_mtu()` → `bt_gatt_exchange_mtu()` (`transport.c:642`, `:886-917`), до 3 попыток с паузой 120 мс при `-EBUSY`/`-EAGAIN` (`transport.c:775-776`). Перед этим — запрос PHY 2M и Data Length с задержками 300 мс и 1000 мс (`transport.c:634-641`).
- Если MTU остался ≤ 23, обмен перезапрашивается каждые 800 мс, до 6 раз (`transport.c:121-122`, `:850-883`).
- Конфигурация стека: `CONFIG_BT_L2CAP_TX_MTU=498` (`omi.conf:123`), `CONFIG_BT_BUF_ACL_RX_SIZE=1024` (`omi.conf:131`), `CONFIG_BT_BUF_ACL_TX_SIZE=2048` (`omi.conf:132`), `CONFIG_BT_CTLR_DATA_LENGTH_MAX=251` (`omi.conf:125`), `CONFIG_BT_GATT_AUTO_UPDATE_MTU=y` (`omi.conf:139`).
- **[не найдено]** Конкретное значение согласованного MTU в коде не зафиксировано — оно зависит от центрального устройства. Как именно Zephyr выводит ATT MTU из этих опций, не проверял: исходников Zephyr/NCS в репозитории нет. По смыслу опции 498 — верхняя граница со стороны прошивки, но это не проверено.
- Буфер под одно уведомление — 517 байт (`MAX_POSSIBLE_MTU`, `transport.c:1063-1064`).
- **Порог отправки:** звук по BLE идёт только при `current_mtu >= 100` (`MINIMAL_PACKET_SIZE`, `config.h:9`; проверка `transport.c:1229`). Пока MTU меньше, кадры при живом соединении выбрасываются (см. раздел 5).

### Фрагментация

- Единица фрагментации — один Opus-кадр (до 160 байт). Несколько кадров в одно уведомление не склеиваются: кадры читаются из очереди по одному (`transport.c:1011-1027`, `:1224`).
- Размер нагрузки одного уведомления: `MIN(current_mtu - 3, осталось_байт_кадра)` (`transport.c:1075`). Длина уведомления = нагрузка + 3 байта заголовка (`transport.c:1099`).
- Если кадр длиннее `current_mtu - 3`, он режется на несколько уведомлений; у каждого свой заголовок с правилами из раздела 2.
- **[вывод]** При кадре ≤ 160 байт и пороге MTU ≥ 100 фрагментация возможна только при MTU от 100 до 162. При MTU ≥ 163 каждый кадр — ровно одно уведомление с `index = 0`.
- **[вывод]** В формуле вычитаются только 3 байта собственного заголовка, а 3 байта заголовка ATT не учитываются (комментарий в `transport.c:504-506` говорит, что `current_mtu` — полный MTU). Значит, полный фрагмент имел бы длину ровно `current_mtu` при допустимой нагрузке уведомления ATT `MTU - 3`. Что стек делает с таким уведомлением, не проверял (исходников Zephyr в репозитории нет). Пример из документации (251 + 75 байт для PCM, `Protocol.mdx:143-147`) к этой прошивке неприменим: PCM она не шлёт.

### Очередь и управление потоком

- Между кодеком и BLE — кольцевой буфер на 32 слота по 162 байта: 2 байта длины + до 160 байт кадра (`config.h:8`, `transport.c:973-975`, `:994-1002`). **[вывод]** 32 кадра × 20 мс ≈ 640 мс звука.
- Если буфер полон, кадр отбрасывается: `write_to_tx_queue` возвращает `false` (`transport.c:1003-1004`), `broadcast_audio_packets` — `-1` (`transport.c:1454-1458`), вызывающий код только увеличивает счётчик монитора (`omi/firmware/omi/src/main.c:70-75`; монитор выключен — `omi.conf:222`).
- Одновременно «в полёте» не больше `CONFIG_BT_CONN_TX_MAX - 2` = 18 аудиоуведомлений; 2 слота зарезервированы под батарею и статус (`transport.c:660-667`, `omi.conf:129`). Поток отправки блокируется на семафоре (`transport.c:1080`), слот освобождается в колбэке завершения передачи (`transport.c:1035-1040`).
- Ошибка `bt_gatt_notify_cb`: до 3 повторов с паузой 1 мс, затем фрагмент и остаток кадра теряются (`transport.c:1072`, `:1092-1127`).
- Уведомления, не запись с подтверждением: характеристика объявлена `READ | NOTIFY` (`transport.c:146-147`), отправка — `bt_gatt_notify_cb` (`transport.c:1103`). Номеров подтверждений и повторной передачи на уровне приложения в `transport.c` нет.

## 5. Что происходит при потере связи

### В момент разрыва — `_transport_disconnected` (`transport.c:669-705`)

- Отменяется перепроверка MTU, сбрасывается счётчик попыток (`:671-672`).
- `is_connected = false` (`:674`).
- SD-модулю сообщается об отключении, `storage_is_on = false` (`:682-683`).
- Если микрофон в AAD-сне, с SD снимается питание (`:686-688`).
- Соединение освобождается, `current_connection = NULL`, `current_mtu = 0` (`:693-697`).
- Семафор аудио-TX инициализируется заново, чтобы поток отправки не остался заблокированным навсегда (`:700-704`).
- Счётчик packet number не трогается (см. раздел 2).

### Куда идёт звук без соединения — поток `pusher` (`transport.c:1215-1255`)

Запись и кодирование не останавливаются. Для каждого кадра из очереди:

| Состояние | Что с кадром | Где |
|---|---|---|
| Есть соединение, MTU ≥ 100, клиент подписан на уведомления | отправка по BLE | `transport.c:1227-1236` |
| Соединения нет, SD включена (`is_sd_on()`) | запись на SD через `write_to_storage()` | `transport.c:1237-1241` |
| Соединения нет, SD выключена | кадр теряется, один раз пишется `Offline storage unavailable` | `transport.c:1242-1247` |
| Соединение есть, но MTU < 100 или нет подписки | кадр **теряется** (на SD не пишется), пауза 10 мс | `transport.c:1229-1231`, `:1249-1252` |

Офлайн-хранилище включено в сборке: `CONFIG_OMI_ENABLE_OFFLINE_STORAGE=y` (`omi.conf:214`); в `Kconfig` по умолчанию `n` (`omi/firmware/omi/Kconfig:11-15`).

### Формат записи на SD (`transport.c:1133-1175`)

- Каждый кадр пишется как 1 байт длины + байты Opus (`OPUS_PREFIX_LENGTH 1`, `transport.c:1133`, `:1143`, `:1165-1166`). BLE-заголовка из раздела 2 в файле нет.
- Кадры копятся в блок 440 байт (`MAX_WRITE_SIZE`, `omi/firmware/omi/src/lib/core/sd_card.h:10`) и отдаются в `write_to_file()` целым блоком (`transport.c:1147-1163`).
- `write_to_file()` кладёт блок в очередь SD; если очередь полна — блок отбрасывается с логом `Write queue full, dropping audio data` (`sd_card.c:1260-1275`). Также отбрасывает, если SD не готова, приостановлена или заблокирована (`sd_card.c:1224-1249`).

### Что теряется на границе

- **[вывод]** Кадры, которые в момент разрыва уже лежали в кольцевой очереди (до 32 кадров ≈ 640 мс), уйдут на SD — поток читает их после того, как `current_connection` стал `NULL`.
- **[вывод]** Кадр, который отправлялся в момент разрыва: `bt_gatt_notify_cb` вернёт ошибку, после 3 повторов кадр теряется (`transport.c:1121-1127`). На SD он не дублируется: ветки отправки и записи взаимоисключающие (`transport.c:1234-1252`).
- **[не найдено]** Что происходит с уведомлениями, уже переданными в BLE-стек, но не доставленными, — это внутри Zephyr, в репозитории не видно. Механизма досылки таких кадров в `transport.c` нет.

### Переподключение

- При новом подключении SD-модулю ставится запрос `REQ_FLUSH` (`sd_card.c:1203-1213`), запрашивается питание SD (`transport.c:612-616`), заново согласуются параметры соединения, PHY, Data Length и MTU (`transport.c:631-643`).
- Запрашиваемые параметры: интервал 7,5–15 мс, latency 0, supervision timeout 400 × 10 мс = 4 с (`transport.c:783-788`). Примет ли их центральное устройство, из кода не следует.
- Накопленное на SD забирается через отдельный storage-сервис (регистрируется в `transport.c:1395-1398`). Его протокол в этой задаче не разбирал.
- **[не найдено]** Явного перезапуска рекламы после разрыва в `omi/firmware/omi/src` нет: `bt_le_adv_start(BT_LE_ADV_CONN, ...)` вызывается один раз при старте транспорта (`transport.c:1400`), колбэка `recycled` нет. Комментарий в `omi/firmware/omi/src/mic.c:372` утверждает, что реклама продолжается. Возобновляет ли её стек сам, зависит от определения `BT_LE_ADV_CONN` в NCS 2.9.0 — не проверял, исходников в репозитории нет.
- **[не найдено]** Таймаутов «считать связь потерянной» на уровне приложения, кроме supervision timeout выше, не нашёл.

Документация про потерю связи и офлайн-хранилище ничего не говорит (`Protocol.mdx`, весь файл).

## Отличия прошивки devkit (`omi/firmware/devkit`)

Смотрел только конфигурацию кодека и формирование заголовка, полностью файл не разбирал.

- Codec ID = **20** — `omi/firmware/devkit/src/config.h:37`.
- Кадр = **160** сэмплов (**[вывод]** 10 мс при 16 кГц; частоту в devkit отдельно не проверял) — `omi/firmware/devkit/src/config.h:25`.
- Битрейт тот же, 32000 — `omi/firmware/devkit/src/config.h:28`.
- Заголовок устроен так же: packet number растёт на каждое уведомление, index — номер фрагмента — `omi/firmware/devkit/src/transport.c:584-588`, `:613`.

Таблица кодеков в документации (`Protocol.mdx:97-103`) соответствует именно этому варианту, а не основной прошивке.
