# Проверка аудиопотока по BLE

Работать из `toolkit/`, интерпретатор `../.venv/bin/python`, результаты в `out/`.
Параметры протокола - только из `docs/omi-audio-protocol.md` и `scripts/omi_protocol.py`.

## 1. Уточнить условия

Нужны три значения. Если пользователь их не назвал, спросить; если просит не спрашивать -
взять значения по умолчанию и явно назвать их в ответе.

- MTU (по умолчанию 498 - верхняя граница из конфига прошивки, не измеренное значение);
- вероятность потери уведомления (по умолчанию 0);
- порог доли потерянных кадров (по умолчанию 0.05).

Для оценки пропускной способности ещё нужны интервал соединения и число пакетов за
интервал. Их задаёт телефон; без них `ble_budget.py` не запускать с выдуманными числами,
а спросить или посчитать несколько вариантов и назвать их вариантами.

## 2. Пропускная способность

```
../.venv/bin/python scripts/ble_budget.py --mtu <MTU> --packets-per-interval <K> --interval-ms <МС>
```

Если спрашивают про буфер или хранилище, добавить `--buffer-bytes <БАЙТ>`.
Код выхода 1 означает «не хватает» по худшему размеру кадра.

## 3. Входной сигнал

Если WAV пользователя нет, сгенерировать:

```
mkdir -p out
../.venv/bin/python scripts/gen_signal.py speech --duration 30 --out out/speech.wav
```

Свой WAV должен быть 16 кГц моно, иначе `check_stream.py` вернёт код 2.

## 4. Прогон потока

```
../.venv/bin/python scripts/check_stream.py out/speech.wav out/rx.wav \
  --mtu <MTU> --loss <P> --max-frame-loss <ПОРОГ> --seed 1 --report out/report.json
```

При ненулевых потерях прогнать не меньше трёх разных `--seed` с отдельными файлами
отчёта: один seed ничего не говорит о разбросе.

## 5. Разобрать отчёт

Смотреть `checks` в `out/report.json`:

- `duration_matches` - главная проверка: длительность выхода совпадёт с входом, только если
  приёмник правильно посчитал число кадров (`duration_s`);
- `gaps_match_dropped` - самопроверка подсчёта номеров: пропусков найдено столько, сколько
  выброшено (`notifications.dropped` против `notifications.gaps_found_by_receiver`). Почти всегда
  истинна и мало говорит о протоколе;
- `frame_loss_within_limit` - `frames.loss_ratio` не выше порога. Доля считается по тому,
  что стенд выбросил на самом деле; настоящий приёмник видит только `frames.lost_by_receiver`.

Если `duration_matches` ложно при MTU 100–162 и `ambiguous_gaps` больше нуля - это известное
ограничение заголовка (нет флага последнего куска), а не ошибка скрипта. Сообщить как
ограничение протокола и предложить MTU от 163.

## 6. Ответ

1. Вердикт: PASS или FAIL, и какая проверка не прошла.
2. Цифры из отчёта: уведомлений отправлено и выброшено, пропусков найдено, кадров потеряно
   и доля, средний и максимальный размер кадра, битрейт, длительность входа и выхода,
   загрузка канала из `ble_budget.py`. Указать команды и seed.
3. Допущения: из блока «Допущения модели» и поля `assumptions`, только относящиеся к вопросу.
4. Отдельно «Проверено на компьютере» и «Нужно проверить на устройстве»: согласованный MTU,
   интервал и число пакетов за интервал, реальный характер потерь, поведение стека BLE,
   размеры кадров кодера прошивки.

Не подбирать seed или порог до PASS. FAIL сообщать как есть.
